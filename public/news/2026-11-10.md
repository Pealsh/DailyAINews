## 【GitHub】meta/astryx — Metaが社内OSS化したReact/StyleX向け「エージェント対応」デザインシステム
**日付**: 2026-11-10時点のGitHub Trending(daily)で確認 ｜ **⭐ 総数**: 約19.8k ｜ **今日**: +3,324(日間トレンド) ｜ **言語**: TypeScript(Trendingページ表示) ｜ **最終更新**: 不明(GitHub API未取得) ｜ **ライセンス**: MIT

astryxは、Meta社内で開発され「同社で最も使われているデザインシステム」とされるReact 19+/StyleX向けのOSSコンポーネントライブラリ(現在ベータ)。150以上のアクセシブルなコンポーネント、ダークモード対応、neutral/butter/chocolate/matcha/stone/gothic/y2kの7テーマ、テンプレート、CLIを含む。最大の特徴は「オープン内部構造」で、`swizzle`コマンドを使うとコンポーネントの完全なソースコードを自分のプロジェクトへコピーして自由に改変できる。スタイルはStyleXで書かれているが、利用側は`className`経由でTailwindやCSS Modulesで上書きできるため、スタイリングの縛りがない。READMEは「人間とAIアシスタントが同じAPI・規約・ドキュメント・CLIで同じように開発できる」ことを明言しており、エージェントがCLIのパスエラーを起こさないよう`package.json`にスクリプトを追加する、CLIをグローバルインストールしてどのフォルダからでもastryxを認識させる、といった具体的な運用上の推奨までREADMEに書かれている。

### 話題の理由 / 注目度の根拠
Metaの社内実績を背景にOSS化された点と、「AIエージェントが人間と同じ規約でUIを組む」ことを明示的に設計目標に掲げている点が、公開直後から日間+3,324という伸びにつながっている。

### 対象読者
React/StyleXでUIを量産し、コーディングエージェントにもデザインシステムへ追従させたいフロントエンドエンジニア。

### 今日試せること
```sh
npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex
npm install -D @astryxdesign/cli
npm run astryx -- component --list
```
`swizzle`で任意のコンポーネントのソースを取り込み、改変できるかを小さく試すとよい。

### 深掘りポイント
`swizzle`によるコンポーネント所有権の移譲と、StyleXのビルドプラグイン(`build`パッケージ)がテーマのCSSカスタムプロパティをどう解決しているか。

## 【GitHub】milind-soni/OpenMausBot — 自分のPC上でClaude/Codex/GrokのCLIを動かす「AIエージェント軍団」チャットアプリ
**日付**: 2026-11-10時点のGitHub Trending(daily/weekly)で確認 ｜ **⭐ 総数**: 約19.6k ｜ **今日**: +1,589(日間トレンド) ｜ **今週**: +7,621(週間トレンド) ｜ **言語**: TypeScript ｜ **最終更新**: 不明(GitHub API未取得) ｜ **ライセンス**: Apache 2.0(`enterprise/`配下は別ライセンス)

OpenMausBotは、xAIのGrok Botに想起を得た独立・非公式のOSS代替で、デスクトップのチャットアプリの連絡先一人ひとりが実際のAIエージェントになる。各ボットはユーザーのPCにすでにインストール・ログイン済みのClaude/Codex/Grok CLIのいずれかでローカル実行され、モデル・人格・接続アプリをボットごとに設定できる。`127.0.0.1`上のローカルハーネスサーバーがエージェントを動かし、会話ログと鍵は`~/.openmausbot`に保存される。シェルコマンドやファイル編集はカード形式の承認待ちUIに出て許可/拒否できる。ボットにはクラウドLinuxデスクトップ(有料サービスBoat、トライアルあり)、分離されたローカルVM、明示的に許可した場合のみ自分のPC本体、という3種類の「コンピュータ」を与えられ、Composio経由で500以上の外部アプリ(Gmail/Slack/GitHubなど)にも接続できる。Markdownファイルからのチーム一括導入、スケジュール/Webhookによる自律起動、MCPサーバー化、ヘッドレスCLI実行にも対応。

### 話題の理由 / 注目度の根拠
「クラウドサービスではなく自分のマシンで、既存のCLIエージェントを人格付きのボット軍団として運用する」という切り口が、日間+1,589・週間+7,621という伸びの速さに表れている。

### 対象読者
Claude Code/Codex/Grok CLIを複数の役割に分けて常駐させたい、ローカル運用志向のエンジニア・パワーユーザー。

### 今日試せること
```sh
npm install -g openmausbot
openmausbot
# チームを一括導入する場合
openmausbot team apply team.yaml
openmausbot run "Room Lead" "<タスク>" --export ./out
```

### 深掘りポイント
ボットに与える「コンピュータ」(クラウドデスクトップ/ローカルVM/本体PC)の権限分離の設計と、Composio経由の500以上アプリ連携がどこまでOAuth一回で使い回せるか。

[リポジトリ](https://github.com/milind-soni/OpenMausBot)

## 【GitHub】max-sixty/worktrunk — 複数のコーディングエージェントを衝突なく並列実行するgit worktree CLI
**日付**: 2026-11-10時点のGitHub Trending(weekly)で確認 ｜ **⭐ 総数**: 約12.3k ｜ **今週**: +2,313(週間トレンド) ｜ **言語**: Rust ｜ **最終更新**: 不明(GitHub API未取得) ｜ **ライセンス**: MIT OR Apache-2.0

worktrunkは、git worktreeの操作をブランチ操作と同程度に簡単にするRust製CLI。`wt switch <branch>`でworktreeを切り替え、`--create`で新規ブランチとworktreeを同時作成、`-x`オプションで切り替え後に`claude`などのコマンドを起動できる。`wt list`は未コミットの変更・mainへの差分・未pushのコミットなどworktreeごとの状態を一覧表示し、`wt merge`はsquash・rebase・mainへのマージ・後片付けを一気通貫で行う。`wt step commit`はステージ済みの変更をコミットし、LLMでコミットメッセージを生成することもできる。依存関係のインストールや開発サーバー起動を自動化するフック、APFS/btrfs/XFS上での共有ビルドキャッシュ、`wt switch pr:123`によるPRチェックアウトも備える。複数のAIエージェントを同時に走らせても作業ディレクトリが分離され、変更が衝突しないことを主眼に設計されている。

### 話題の理由 / 注目度の根拠
「1タスク1エージェント1worktree」で並列開発する運用が広がる中、素のgit worktreeコマンドの煩雑さを解消する専用CLIとして週間+2,313という伸びを見せている。

### 対象読者
Claude Code/Codex等を複数同時に走らせ、ブランチ単位で並列にタスクを進めたいエンジニア。

### 今日試せること
```sh
brew install worktrunk && wt config shell install
wt switch --create feature-auth
wt switch -x claude -c feature-a -- "ユーザー認証を追加して"
wt list
```

### 深掘りポイント
`wt merge`が行うsquash→rebase→merge→後片付けの一連の流れと、ビルドキャッシュをworktree間で共有する仕組み(APFS/btrfs/XFS依存)。

[リポジトリ](https://github.com/max-sixty/worktrunk)

## 【AI機能】GitHub Copilot in JetBrains Air — 既存のCopilotサブスクリプションがJetBrainsの新IDEでそのまま使える
**日付**: GitHub公式changelog 2026-11-03付「GitHub Copilot is now available in JetBrains Air」、JetBrains公式ブログでも同時期に紹介(直近で注目度が高いトピックとして収録。github.blog/blog.jetbrains.comへは本セッションのネットワーク制限で直接アクセスできず、検索結果のスニペットに基づく)

JetBrainsが提供する新しいAIネイティブIDE「Air」のエージェントピッカーから、GitHub Copilotを選択できるようになった。JetBrains公式ブログによれば、Air上でのCopilotはACP(Agent Client Protocol)経由でローカル実行され、Air Teamsへの加入は不要だが、GitHub Copilotのサブスクリプション自体は別途必要。タスクの課金はJetBrains AI創设のクレジットではなくユーザー自身のCopilotプランに対して行われる点が特徴で、個人のCopilotプランと組織のプランのどちらを使うかをタスクごとに選ぶことはできない。なおクラウド実行タスクを使うにはAir Teamsへの加入が必要になる。

### 対応製品/機能/制約
- 対応製品: JetBrains Air(JetBrains系IDE群のAIネイティブ版)
- 必要環境: GitHub Copilotサブスクリプション(個人または組織)。クラウドタスクにはAir Teams加入が別途必要
- 制約: タスクごとに個人/組織のどちらのCopilotプランを使うか選択できない
- 関連: GitHubのCLI release note(11月2日付)では`copilot -p --plan`実行時にplanモードを抜ける操作案内(Shift+Tab)が表示されなくなる修正があったと報告されている(検索結果の二次情報、未検証)

### 話題の理由 / 注目度の根拠
Copilotが単一エディタの機能から「サブスクリプションに紐づくサービス」としてIDEをまたいで使えるようになった動きの一環で、GitHub/JetBrainsの両公式チャンネルがほぼ同時に取り上げている。

### 対象読者
JetBrains系IDE(IntelliJ IDEA等)とVS Code/Claude Codeなど複数エージェントを併用している、またはAirの採用を検討しているエンジニア。

### 今日試せること
JetBrains AirをインストールしたうえでGitHub Copilotサブスクリプションがあれば、エージェントピッカーからCopilotを選ぶだけで既存プランのまま試せる。クラウドタスクを試す場合のみAir Teamsへの加入が必要になる点に注意。

### 深掘りポイント
ACP(Agent Client Protocol)がCopilotのようなサードパーティエージェントをIDEに接続する仕組みと、タスク単位でのプラン選択ができない制約が組織利用でどう影響するか。
