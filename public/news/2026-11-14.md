## 【GitHub】alibaba/open-code-review — 「決定的パイプライン+LLMエージェント」でレビューのブレを抑えるAIコードレビューCLI
**日付**: 2026-11-14時点のGitHub Trending(daily)で確認 ｜ **⭐ 総数**: 50,540(Trendingページ表示) ｜ **今日**: +206(Trendingページ表示) ｜ **言語**: Go(リポジトリのgo.mod/cmd構成より) ｜ **最終更新**: 2026-11-13(リポジトリのcommitsページで確認、直近コミットは「zero-finding PR summariesでの警告表示」修正) ｜ **ライセンス**: Apache-2.0

Alibaba Groupが社内ツールを公開したAIコードレビューCLI「`ocr`」。Gitの差分をLLMエージェント(ツール利用可能)に渡して行単位の構造化レビューコメントを生成する一般的なエージェント型レビューに対し、本ツールは「ファイル選定の精度」「関連ファイル(例: ロケールファイルの対応関係)の束ね」「コメント位置・内容の検証」を固定ロジック(決定的パイプライン)に任せ、LLMの裁量はレビュー用プロンプトとツールセットの判断に限定する設計。自前で50リポジトリ・200PR・1,505件の注釈付き問題からなる「AACR-Bench」を使い、同じモデルを使ったClaude Codeのエージェントレビューと比較して、再現率はやや下げつつ精度・F1が高く、トークン消費は約1/9で済むと報告している。GitHub Actions/GitLab CI/GitFlic CI/Gerrit向けのCI連携と、Claude Code/Codex/Cursor/Kimi Code/OpenCodeへのホストエージェント委任(`ocr delegate`)の両方を備える。

### 話題の理由 / 注目度の根拠
本日のGitHub Trending(daily)で日間+206、総スター50,540。「AIエージェントにレビューを丸投げすると網羅性やコメント位置がブレる」という実務上の不満に対し、固定ロジックとLLM判断の境界を明示的に切り分けた設計と、独自ベンチマークでの比較数値を公開している点が注目されている。リポジトリのトピックにも`agent`・`agent-skills`が付けられている。

### 対象読者
CIにAIコードレビューを組み込みたいが、既存のエージェント型レビューツールの出力が不安定で困っているチーム。Claude Code/Codex等のコーディングエージェントにレビュー専用の委任先を持たせたい開発者。

### 今日試せること
```sh
npm install -g @alibaba-group/open-code-review
ocr config provider   # LLMプロバイダーを設定(OpenAI/Anthropic互換)
ocr config model
ocr review             # 作業中の差分をレビュー
ocr review --from main --to feature-branch   # ブランチ間レビュー
ocr scan --path internal/agent               # 差分なしでディレクトリ全体を精査
ocr delegate preview   # ホストのコーディングエージェントにレビューを委任(OCR側のLLM設定不要)
```

### 深掘りポイント
AACR-Benchでの比較が「再現率を意図的に下げてでも精度とトークン効率を取る」設計判断であることが明記されている点は、自分のレビュー用途がFP(誤検知)を嫌うのかFN(見逃し)を嫌うのかで採用判断が分かれるポイント。OpenTelemetryテレメトリとブラウザ型セッションビューアも同梱されており、社内でのレビュー監査ログ運用の参考になる。

[リポジトリ](https://github.com/alibaba/open-code-review)

## 【GitHub】backnotprop/plannotator — エージェントのplanとPRにブラウザから注釈を返す「ループに留まる」ためのワークスペース
**日付**: 2026-11-14時点のGitHub Trending(daily)で確認 ｜ **⭐ 総数**: 10,408(Trendingページ表示) ｜ **今日**: +100(Trendingページ表示) ｜ **言語**: TypeScript(Bunモノレポ) ｜ **最終更新**: 2026-11-13(リポジトリのcommitsページで確認、直近はPR #3307のマージ) ｜ **ライセンス**: Apache-2.0 / MIT(デュアルライセンス)

Claude Code・Codex・Gemini CLI・OpenCode・Pi・Copilot CLIなど複数のコーディングエージェントのフック(hooks)に割り込む、ローカル実行のブラウザ型レビューアプリ。エージェントがplanを提示したりタスクを完了したタイミングでアプリが自動的にブラウザを開き、planやMarkdown/HTML/URL/直前の返答に注釈を付けて承認・却下でき、その修正指示(フィードバック)が次の指示としてそのままエージェントに返る。GitHub/GitLabのPR・MRを取り込んでdiffにコメントし、エージェントへ送り返すレビュー機能や、複数エージェントからの質問・ファイル・レビュー依頼を1つのローカルウィンドウに集約する「Plannotator Inbox」も備える。設定はフック呼び出しごとにランダムポートが変わるためクッキーに保存され、リモート/SSH利用では固定ポート(19432)と`PLANNOTATOR_REMOTE`で対応する。

### 話題の理由 / 注目度の根拠
本日のGitHub Trending(daily)で日間+100。「エージェントにplanを立てさせて承認してから実装させる」Plan Modeの普及に伴い、plan承認・差分レビューをCLIのテキストではなくブラウザUIで素早く行いたいという需要に応えている点、リリースにSHA256チェックサム・SLSA provenance・SBOMを付け利用時のテレメトリを取らないという運用面の作り込みも評価されている。

### 対象読者
Claude Code/Codex等でPlan Modeを使い、plan承認やPRレビューをテキストのやり取りだけで済ませたくない開発者・チーム。複数エージェントを並行稼働させ、承認待ちの通知を1画面に集約したい人。

### 今日試せること
```sh
curl -fsSL https://plannotator.ai/install.sh | bash
# エージェント内のスラッシュコマンド/CLIから
/plannotator-annotate README.md
/plannotator-review
/plannotator-review <github-pr-url>
plannotator inbox
```

### 深掘りポイント
リモートモード(`PLANNOTATOR_REMOTE`)は固定ポートで全インターフェースにログインなしで待ち受けるとREADMEに明記されており、共有サーバーで使う場合はネットワーク側での保護が前提になる点は本日取り上げたQwen CLIのデーモンモードと同種の注意点。「Workspacesが今後のホスト型チームコラボの本線で、レガシーなリンク共有は非推奨化予定」という開発方向性も、チーム導入前に確認したい。

## 【AI機能】Claude Code「Code Mode」— Claudeがツール呼び出しの代わりにJavaScriptを書いて実行する実験的機能
**日付**: 2026-11-12、Claude Code v2.1.323のリリースで追加(code.claude.com公式ドキュメントで確認) ｜ **現在の最新バージョン**: v2.1.325(2026-11-13公開、npm registryで確認)

通常のClaude Codeは、Bash/Read/Edit等のツールを1つ呼んでその結果を読み、次の判断をする、という往復を繰り返す。Code Modeを有効にすると、Claudeはその代わりに複数のツール呼び出しをまとめた1本のJavaScriptコードを書き、Claude Codeのセッション内でそのコードを実行する。公式ドキュメント掲載のサンプルでは、`rg`でファイルを検索し、見つかったファイルを`edit`で書き換え、`npm test`を実行して結果を返す、という3段の処理を1回のコード実行で済ませている。会話上に表示されるのはeditのdiffなどツール呼び出しの結果で、コード自体は`Ctrl+O`で開く文字起こしビューアでのみ確認できる。多数ファイルにまたがる同種の変更、検索結果をLLMに読ませる前にコード側で絞り込みたい場合、並列実行できる独立したコマンド群がある場合などに向くとされる。

### 対応製品/機能/制約
- 対応バージョン: Claude Code v2.1.323以降(ネイティブビルド)。古いバージョンは「it isn't open to your account yet」という理由付きでCode Modeなしに起動する
- 対応モデル: Claude Opus 5.5・Sonnet 5.5・Haiku 5.5・Fable 5.2(それより前のモデルは未対応)
- 有効化: 環境変数`CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`(シェルまたは`~/.claude/settings.json`の`env`ブロック)。プロジェクト側の設定ファイルでは無視される(クローンしたリポジトリから勝手に有効化されない安全策)
- 制約: Amazon Bedrock/Google Cloud/Microsoft Foundry/独自ゲートウェイ経由では使用不可(Anthropic API直結のみ)。HIPAA構成やゼロデータリテンション設定の組織では使えない。対話型ターミナルセッション限定で、`-p`・Agent SDK・VS Codeパネル・デスクトップアプリ・クラウドセッションでは動作しない。1回のコード実行は原則10分でタイムアウト(バックグラウンド実行なら最大2時間)
- 現状: デフォルトで無効の実験的機能。`managed settings`で組織単位に強制無効化も可能

### 話題の理由 / 注目度の根拠
「エージェントにツールを1個ずつ呼ばせるのではなくコードを書かせて一括実行させる」というCode Mode的パターンは、Cloudflareが提唱したMCPのコード実行パターンを踏襲した業界共通の潮流(AI SDKやDocker Agent等の他実装でも採用)で、Claude Code本体への実装は大規模エージェントツールのトークン消費削減策として注目されている。ドキュメントが権限チェック・フック・長時間実行時の挙動まで細かく規定している点から、実験的機能としては作り込みが進んでいることが伺える。

### 対象読者
多数ファイルへの同種変更や、検索結果のフィルタリングを含む定型タスクをClaude Codeに任せているパワーユーザー。トークン消費やラウンドトリップ回数を減らしたい、ツール呼び出し主体のエージェント運用をしているチーム。

### 今日試せること
```sh
claude --version   # v2.1.323未満なら
claude update
CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude
# 起動時に「Yes, turn on Code Mode」を選択
# セッション内で例えば
# "このプロジェクトの全Markdownファイルを読んで、存在しないローカルファイルへのリンクを一覧にして"
# と依頼し、Ctrl+Oで生成されたJavaScriptコードを確認する
```

### 深掘りポイント
Auto modeでは「個々のツール呼び出し」ではなく「生成されたコードそのもの」を分類器が審査する仕組みに変わるため、実行時に動的に決まる値(検索結果から取得したパス等)はレビューされないとドキュメントが明記している。`PreToolUse`フックで`REPL`ツール(Code Modeの実行主体)にマッチさせ`tool_input.code`を読むことで、コード内容自体をチェックできるという権限設計は、エージェントにコード実行権限を与える際の監査ポイントとして参考になる。
